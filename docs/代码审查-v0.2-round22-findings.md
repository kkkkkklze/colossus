## 1. 快照 / 续播（问题 1）

### P2-1 `resumeFrom` 用赋值而不是或运算——位图半侧可以倒退，直接违反它自己 javadoc 的"不重放"

`state/FrameRunner.java:199-208`（工作区未改，＝`b3f7949` 原样）：

```java
this.lastTick = Math.max(tickAt, this.lastTick); // 绝不允许倒退：倒退会重放整段窗口
...
this.fired[i] = passed || claimed;
```

`lastTick` 走了 `Math.max`，`fired[i]` 却走**覆盖**。于是一份比当前进度更旧的快照会把"在 `(tickAt, lastTick]`
之间已经触发过、但 `from > tickAt`"的一次性帧**解除武装**，下一个 `advance` 就在窗口里再触发一次。

反例（我按代码手推，不是猜）：帧表 `[0]=between(2,10)`、`[1]=between(20,25)`，`advance` 到 21（0 号在 2
触发、1 号在 20 触发，`fired=[true,true]`）；此时 `resumeFrom(5, 0L)` → `lastTick` 仍是 21，但
`fired[1] = (20<=5) || false = false`；`advance(22)` → 22∈[20,25] 且 `fired[1]==false` → **1 号再触发一次**。
这正是提交信息里那句"存档错一位＝白挨一刀"要防的形态，只是它换了入口。

为什么成立（判据缺失的位置）：`test/StateSelfTest.java` 里五处 `resumeFrom` 调用（:421、:432、:442、:456 两处）
**全部作用在从未 `advance` 过的新 runner 上**——`:415` 那个推进过的 runner 只是被读了 `lastTick()/firedBitmap()`，
再没人对它 `resumeFrom`。所以"旧快照 + 已推进"这条路径零覆盖，"同一快照恢复两次"（:456-458）测的是**新表**恢复两次，
恰好绕开了唯一的非幂等方向。

第二半落地时这条会变成真故障：`entity/AttackState.java:26` 是 `onStart` 里 `move.newRunner()` 建**新表**，
所以现在生产路径碰不到；但快照一旦接线，"恢复动作晚于第一 tick `advance`"（存档写入在前、崩溃前实体又 tick 了
若干帧；或 `resumeFrom` 被调两次）就是这条路径。

建议：`this.fired[i] = this.fired[i] || passed || claimed;`（tick 与位图两侧都只许前进），并把 `:200` 那句注释
改成"两侧都不许倒退"。补一条今天会红的断言：先 `advance` 过 1 号窗口，再用 `(tickAt=1, bitmap=0)` 恢复，
后续 tick 不得触发任何帧。

### P3-2 `resumeRejection` 从不比 `stateTick + elapsed`——它漏的正是它名字里那句话

`state/FrameRunner.java:220-230`：`stateTick` 与 `elapsedTicksWhileLoaded` 各自单独和 `durationTicks` 比，
两边都放行时**合起来可以远超整招长度**：`resumeRejection(95, 100, 100)` 返回 `null`（放行），
而这一刻这一招已经在第 195 帧、整招只有 100 帧。javadoc（`:214-216`）写的是"只有超出整招长度才拒"，
按字面应该是 `stateTick + elapsed > duration`。

危害有界（我核过接线点，所以不升 P2）：`advance` 的返回值不影响状态机结束——
`entity/AttackState.java:33,40` 的 `tick` 取自 `ActiveState.tick()`，结束判据是 `tick >= move.duration()`，
不是 `runner.lastTick()`。所以后果是"恢复后继续播一段早该结束的招（持续帧按 tick 纯函数继续放）"，
不是卡死。

判据侧：`test/StateSelfTest.java:510-515` 五条 `resumeRejection` 全是 `!= null`，
唯一一条"放行"是 `resumeRejection(5, 20, 14) == null`——正好避开了这个洞（5+14=19 < 20）。
建议加 `if (stateTick + elapsedTicksWhileLoaded > durationTicks) return "...";`
（或明确写"两道分开比"并说明为什么可以合起来超），并把这条断言换成 `resumeRejection(95,100,100) != null`。
另外那五条只钉"有没有拒"，没钉"理由能不能进日志"——`javadoc:218` 明写"给出一条能直接进日志的理由"，
建议至少钉一条"理由串里含有那个越界的数字"（第二半接 logger 之前把口径钉死）。

### P3-3 位图边界的**真实后果是别名不是截断**；datapack 那个 64 仍是第二个私有字面量

两件事，都在 `state/FrameRunner.java:115-122`（工作区未改）：

1. 注释说"让它静默截断会把第 65 帧之后的触发状态丢掉"。实际机制更糟：`firedBitmap()`（`:177`）与
   `resumeFrom`（`:205`）都是 `1L << i`，**Java 的 long 移位取模 64** ⇒ 第 65 帧（i=64）不是"存不下"，
   而是**写到第 1 帧的 bit 0 上**。没有这道 `build()` 守卫时，一次恢复会同时"重放 1 号"和"缴械 65 号"。
   这句话必须写进注释：这道闸是防别名，不是防截断——否则下一个人会以为"大不了少存几位"就把它放宽。
   顺带：边界 64（i≤63，含符号位）本身是安全的，`bits |= 1L << 63` 与 `(bitmap & (1L<<63)) != 0L`
   都是符号安全的写法（这点审过，见 §5）。
2. 注释声称"与 datapack 侧同值的 `MoveCodec.MAX_FRAMES_PER_MOVE` 同一规则"——但
   `move/data/MoveCodec.java:43` 是 `private static final int MAX_FRAMES_PER_MOVE = 64`，**第二个独立字面量**，
   两处只在注释里互相指认。这和 `a8337dc` 自己修的 P3-4（`Live.mirrorKey` 与 `key()` 两处各写一份位运算）
   是同一个病。工作区已经把 Java DSL 那条口接到 `FrameRunner.MAX_PERSISTABLE_FRAMES`
   （`move/MoveSetBuilder.java` 的 `done()`），只剩 datapack 这条口没接：让 `MoveCodec` 直接引那个 public 常量。

（另外登记一条：`build()` 的守卫落在 `MoveDef.newRunner()`（`move/MoveDef.java:138-144`，每次出招都走）
而不是注册期——工作区那份未提交的 `MoveSetBuilder.done()` 已经补了注册期的同值拒并配了断言
（`test/StateSelfTest.java:483-508`），这条我不重复开单。）

### P3-4 位图下标＝注册序，而快照里没有帧表指纹

`resumeFrom` 用 `(bitmap & (1L<<i))` 按**下标**解释每一位，下标的定义来自 `Builder` 的注册序
（`FrameRunner.java:81` 注释"注册序即触发序"）。第二半计划的三个 NBT 键是"招名 + 招内 tick + 位图"
（提交信息原话），也就是说：**同一个招名在 datapack 重载后帧序变了，旧位图会被按新表解释**——
往右移一帧就是"上一发的位扣到下一发身上"（要么抑制掉新的一发伤害，要么放行已经过的一发）。
建议第二半落地时加第四个键（帧表 `from` 序列的 hash，或 `MoveDef` 的版本/内容指纹），
不匹配就走 `resumeRejection` 那条 idle + 日志的分支——那才是"宁少发一次不发两遍"这句在存档侧的完整形态。
同时提醒一个本仓已知的族：写 `putLong` 就读 `getLong`，别用 `contains(key, Tag.TAG_LONG)` 当"能不能读"的判据
（`contains` 是精确类型等值，而 `getInt/getLong/getDouble` 内部走 mask=99），否则"类型宽一点的合法存档"
会被判成缺键，而"缺键回 idle"这条路径正是第二半要新加的。

## 2. `TailLedger` 驱逐序 / `emissions` 上界 / `retire`↔`noteEmission` 时序（问题 2）

### P2-4 时钟 skew 下 `book` 的 `end <= start` 判据会**整条拒记已发生的发射**，而 `emissions` 已被消费

`env/TailLedger.java:94-99`（工作区当前形态，`a8337dc` 里是 `:75-80`）+ `:122`：

```java
long[] em = emissions.remove(mirrorKey);   // 无条件消费
if (em == null) return false;
long end = Math.min(nominalEnd, em[1] + 1L);
book(mirrorKey, (int) em[0], particleLife, start, end);
```

`em[1]` 是**客户端本地 tick**（`client/TelegraphClient.java:392` 传的是 `now = mc.level.getGameTime()`），
`start` 是**服务端登记时刻**（同一个时基，但 `:232` 明确允许 `now` 比 `startGameTime` 小达一整个 span——
"本地钟落后不超过一个寿命就照样画"）。于是 `end = min(nominalEnd, now+1)` 可以 `<= start`，
`book` 的 `end <= start` 那一支（`:122`）直接 `return`：**粒子真撒过、尾段一条没有**；
而 `:95` 已经把 `emissions` 条目 remove 掉了，后面到期清扫（`TelegraphClient.java:206-212`）第二次
`retire` 只能空手返回 false ⇒ 永久性漏记（低报＝本仓认定的危险方向）。

工作区新加的 `TelegraphBudget.tailAlive`（`:115-125`，`now <= start` 时交一生峰值）恰好承认了这类 skew 存在，
但那一支永远看不到这条被 `book` 拒掉、压根没进 `entries` 的账。

建议（一行）：`long end = Math.min(nominalEnd, Math.max(em[1] + 1L, start + 1L));`——"记过发射就不许有零长度窗口"，
把"要不要记"留在 `em == null`（从没发射）那一处判，别让时间量把已发生的事实抹掉。
或者：`book` 拒绝时 `return false` 且 `retire` 把 `em` 塞回去（保留事实），但前者更简单。

### P3-5 `retire` 的新返回值有一处会说谎

`env/TailLedger.java:94-99`：`return entries.containsKey(mirrorKey);`。当 `book` 因为
`rate <= 0 || end <= start` 拒绝入账时，如果这个键**上一轮已经有一条尾段在账上**（同键覆盖语义下完全可能：
先 retire 成功入账 → 圈又活了 → `cancel` 撤账失败/未撤 → 再 retire 被拒），`containsKey` 返回 true，
而 javadoc（`:85-90`）写的是"是否真的生成/替换了一条尾段"。让 `book` 返回 `boolean` 并把它交出去即可。
（这条只在未提交的工作区里存在，所以只登记不开 P2。）

### P3-6 `MAX_EMISSIONS` 仍然没有推导、也没有能断言的口子

工作区给 `emissions` 换了逐出策略（按 `lastEmit` 最老，`TailLedger.java:55-72`）并补了溢出断言
（`test/StateSelfTest.java:797-805`），比 `a8337dc` 的插入序 FIFO 强（那条会把 warn=1200 的在途长预警挤掉）。
残留两点：

1. `private static final int MAX_EMISSIONS = 128;`（`:48`）——`MAX_ENTRIES` 是 public、这个不是，
   于是断言只能把 128 **写成字面量**（工作区新测试正是 `for (int i = 0; i < 128; i++)`），
   常量与测试之间没有链接。改 public，测试引常量。
2. 128 这个数没有推导（提交信息自己登记了"`TAIL_BUDGET_PERCENT` 的推导未做"，这个是同一类欠账）：
   键空间是 (bossId, viewId)，单 Boss 上限 `HARD_MAX_TELEGRAPHS = 32`（`entity/ColossusBossEntity.java:278`），

### P2-7 "哪一 tick 算真发射"这个新性质留在了四条门够不着的地方（结构性，非单点错）

`a8337dc` 把发射事实从 `Live.lastRate` 搬进账本是对的（`Live` 每次投影换实例重建），但它把**事实的判据**
留在了 `client/TelegraphClient.java:379 / 388 / 392` 三个 early-return 的相对位置上：

```java
if (mc.player != null && !(nearOutlineDistSq(...) <= PARTICLE_CULL_DIST_SQ)) return;  // 379 距离剔除
...
if (plan.empty()) return;                                                             // 388 额度不足

liveParticleEstimate += plan.liveCost();                                              // 393
```

今天这个摆放**是对的**（379/388 都在 392 之前 ⇒ 没撒粒子就不记 ⇒ 不是幽灵账；232 那条"钟落后超一个寿命才不画"
也在 392 之前）。问题是**没有任何纯类断言钉住这个先后**：把 392 挪到 379 之前，或给 `spawnOutlineParticles`
新加一条落在 392 之后的 early-return（少撒了粒子却记满率＝低报；反之＝幽灵账），
`colossusSelfTest` 141 条会全绿——因为四条门永不执行 `client/*`（这条 `DESIGN §4` 与 `TailLedger` javadoc
`:10-13` 都自己写明）。这正是轮 20 P1-1 的同族，只是从"账本没被跑过"变成了"账本的输入面没被跑过"。

提交信息里登记的 `env/OutlineFrame`（把"投影→账本"整段抽成零 MC 纯类）就是这一条的修法，**不能只做一半**：
最低成本的版本是在 `TelegraphBudget` 里放一个纯函数
`boolean emitsThisTick(boolean culledByDistance, boolean outOfBudget, boolean clockBehind)`，
或直接让 `Outline` 带一个 `emittedThisTick` 判据，然后在自检里断言
"三个条件任一成立 ⇒ 不产生 noteEmission 事实；三者全假 ⇒ 记的 `rate` 等于实际 `addAlwaysVisibleParticle` 的调用次数"。
后者还能顺手把 `rate` 与真实发射数的等式（现在是 `for (int k = 0; k < plan.ratePerTick(); k++)`，`:398`）钉住。

### P3-8 镜像键没有"代"分量：实体 id 复用时新圈会撤掉旧圈还没散完的账

`client/TelegraphClient.java:265-267` `key(bossId, viewId)`；`viewId` 由
`entity/ColossusBossEntity.java:392` 的**实例字段** `++this.telegraphSeq` 给出，而 `telegraphSeq`
只在读档时从"还活着的 view"续号（`:1735`：`if (v.id() > this.telegraphSeq) this.telegraphSeq = v.id();`），
没有 in-flight view 时新实例就从 1 重新开始。于是**实体 id 被复用时，新 Boss 的 viewId 与旧 Boss 尚在飘的
余晖同名**。后果两条：

- `TelegraphClient.java:195` `TAILS.cancel(key)` 把旧那一发的尾段撤账；紧接着 `:199` `ZONES.put(key, new Live(...)`
  覆盖旧 Live ⇒ 旧 Live 再也没有第二次 retire 的机会 ⇒ 记不到账的在场粒子（低报）。

## 4. 只是复述实现的断言（问题 4）

按本仓"<= 那两条是废断言"的标准，下面五条**判据强度不足**，每条都给了能跑红的替代式：

1. **P2-级别（按本仓规矩算废断言）** `test/StateSelfTest.java:775-776` `dropsSlowest`：
   `evict` 的夹具里 `end = 9000+i` 与插入序同向递增，所以 **80 号同时是"end 最大"和"最新插入"**。
   把逐出策略从"end 最大者"改成"逐出刚插入的那条"（新来的直接不入账），`size()==64 &&
   contains(1L) && !contains(80L)` 三条**同时保持为真** ⇒ 这条断言测不到它的 check 名（"drops the
   slowest-decaying entry"）。修法：让一条**中间**的键 end 最大（例：`evict.noteEmission(40L, 5, 99_000L)`），
   断言 `!evict.contains(40L) && evict.contains(80L)`。（`contains(1L)` 那半边有效——纯 FIFO 逐出会把它剔掉。）
2. `test/StateSelfTest.java:766` `crowded` 夹具被本批 P2-3 的"窗口收窄"顺手改造成退化夹具：
   名义 end 写的是 `10_000L + i`，经过 `retire` 的 `min(nominalEnd, em[1]+1)` 之后 **400 条全部塌成 `3001`**
   （`noteEmission(i, 5, 3_000L)`）。于是那 400 次 `book` 走的溢出分支里 `end > worstEnd` 恒不等 ⇒
   逐的其实是插入序最老的一条。`capped`（`:770`）本身只要"总和 > 500"就成立，所以这条**没坏**，
   但它已经不再测"按 end 逐出"，而注释（`:767`）与提交信息都还当它在测。把 `noteEmission` 的 tick 也做成
   `3_000L + i` 就恢复成有梯度的夹具。
3. `test/StateSelfTest.java:770-771` `capped` 的左半边
   `tailBooked == ceiling * TailLedger.TAIL_BUDGET_PERCENT / 100` **就是被测类 `TailLedger.java:150` 的式子**，
   常量也取自被测类。把 25 改成 90，check 名里"booked to exactly 25% of the ceiling"当场变谎而断言全绿。
   写数字（`== 500`）或另加 `TAIL_BUDGET_PERCENT <= 25`（"装饰不得过半"是策略，不是实现细节）。
   右半边 `tailUncapped > tailBooked` 是真判据，留着。
4. `test/StateSelfTest.java:415` `runner.firedBitmap() != 0L`：只钉"有位被置上"，不钉"置的是第几位"。
   那张表只有一帧 ⇒ 改成 `== 0b1L` 就顺手钉住"位图下标＝注册序"这条隐式契约（P3-4 讲的那个指纹问题
   落地前，这是唯一能红的门）。同理 `:451` 的 `bits` 只被自比较用（`b1`/`b2` 同一份），也没钉内容。

   `if (frames.size() < 64 && (bitmap & (-1L << frames.size())) != 0L)` → 视为损坏、按 P2-1 的口径处理

## 5. 审过且成立（我确认过、不需要改的关键判据）

1. **位图 64 的边界是"真上界"而不是"够用"**：`build()`（`:118`）拒 `> 64`，`firedBitmap`（`:177`）与
   `resumeFrom`（`:201`）的 `1L << i` 因此恒有 `i <= 63`；`bits |= 1L<<63` 与 `(bitmap & (1L<<i)) != 0L`
   对符号位都是安全的，且这个写法**没有**用 `>>`（算术移位会带符号扩展，将来若有人重写成
   `(bitmap >> i & 1) != 0` 就会在第 63 位出问题）。64 帧的表能 build、65 帧不能，两头都有断言
   （`StateSelfTest.java:462-481`）。
2. **持续帧不参与位图既不会重播也不会漏播**：`advance`（`:138-144`）对 repeating 帧在读写 `fired[]`
   之前就 `continue`，所以 `firedBitmap()` 里那些位恒为 0（口径自洽）；触发只由
   `(tick - from) % period == 0` 决定，而 `advance:132` 的 `tick <= lastTick` 闸门保证同一 tick 不会走两遍 ⇒
   恢复不可能让已过的拍补放，也不可能同 tick 双放。`StateSelfTest.java:438-446` 用具体序列
   `[7,10]` 钉住了这条（不是式子复述）。`fired[]` 对 repeating 帧恒 false 也意味着
   `MAX_PERSISTABLE_FRAMES` 按全部帧计数是**保守**方向（浪费位不会漏状态）。
3. **`resumeFrom` 对 `tickAt` 倒退的 tick 半侧确实不倒退**：`Math.max` + `advance` 的 `<=` 早退，

   结束判据来自 `ActiveState.tick()`（`AttackState.java:33,40`），不来自 runner。
