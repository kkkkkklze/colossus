## 1. `resumeFrom` 位图半侧只许前进 / 帧表下标契约（问题 1）

### 轮 22 残留面回读：P2-1 真修掉了

`state/FrameRunner.java:214` 现在是 `this.fired[i] = this.fired[i] || passed || claimed;`，
`lastTick` 走 `Math.max`（`:202`）、位图走 `||`（`:214`），两侧同向 ⇒ **位图半侧确实只许前进**。
轮 22 那个反例（`[0]=between(2,10)`、`[1]=between(20,25)`，advance 到 21 后 `resumeFrom(5,0)`）
在新代码下 `fired[1]` 保持 true，`advance(22)` 不再补放。这一条关闭。

### 持续帧不参与位图：本轮重推，仍然既不漏放也不补放

`advance`（`:140-147`）对 repeating 帧在读写 `fired[]` 之前 `continue`；`resumeFrom`（`:205`）
同一判据 `if (f.repeating()) continue;`。两侧口径自洽，且持续帧的触发只由
`(tick - from) % period` 决定，`:134` 的 `tick <= lastTick` 闸门挡住同 tick 双走。
`||` 的改动**不影响**这一族（repeating 位恒 0，OR 恒等）。✓

### 1-A（P3）`resumeFrom` 对"位图里有越界位"仍然照单全收，而 `||` 让这个状态永久不可逆

**【已核到 path:line】** `state/FrameRunner.java:201-216`（整个方法体内没有任何 `frames.size()` 越界位检查）
+ 判据侧 `resumeRejection`（`:228`）压根不收 `bitmap` 参数。
轮 22 §4 第 5 条开出的修法（`if (frames.size() < 64 && (bitmap & (-1L << frames.size())) != 0L)` 视为损坏）
**本批没有落地**。改完之后新表现是：`||` 让"被越界位缴械"比覆盖式更硬——覆盖至少还可能被后一份
正常快照纠正，`||` 之后**同一 runner 上再恢复多少次都解不开**。危害方向仍是安全侧
（整招静音、不发两遍），且 `AttackState` 目前用 `newRunner()` 建新表（轮 22 已核），
所以维持 P3 不升，但它是轮 22 唯一一条"修法写明了却没做"的条目。

### 1-B（P2）帧表顺序变了的时候：`||` 把"错位"从双向漂移压成单向**永久静音**，而指纹这道闸仍然没有

**【已核到 path:line】** `state/FrameRunner.java:177-183`（`firedBitmap` 按 `fired[]` 下标）、
`:203-207`（`resumeFrom` 按 `frames.get(i)` 下标解释每一位）、`move/MoveDef.java`（`newRunner()` 每次出招新表）。
轮 22 P3-4 提的"快照里加第四个键＝帧表指纹"**未落地**（`grep` 全仓无 `fingerprint`/帧表 hash 相关代码）。
新表现值得单独立一条，因为它和轮 22 描述的形态不同：

- 覆盖式（旧）时，一份"帧序变了"的快照会**同时**造成"多放"（新帧 i 恰好没被置位）和"少放"。
- `||` 式（新）把"多放"那一半彻底消掉了，代价是"少放"那一半变成**不可恢复**：datapack 重载把
  一发作了 20 帧改成 21 帧、或作者插入/删除了一帧，旧位图里第 k 位指向的就是**另一发伤害帧**，
  续播后那一发在整个窗口内一次都不触发，而且日志里没有任何痕迹（`resumeRejection` 只比 tick 与
  duration，看不见位图）。

建议：与其等第二半接 NBT，不如现在就在 `resumeFrom` 上加一个**廉价指纹参数**
（`resumeFrom(int tickAt, long bitmap, long framesDigest)`，digest 由 `MoveDef` 侧算：
`(from,to,period)` 序列的 FNV-1a）。digest 不匹配 ⇒ 整份快照作废走 idle（这才是 javadoc
`:189` 那句"不补偿、不重放"的完整版）。`MoveDef` 已经持有了不可变帧表，digest 可以在构造期算一次存字段。

## 2. `TailLedger.retire` 的窗口下限与 `book` 的返回值（问题 2）

### 轮 22 残留面回读：P2-4 / P3-5 都动了，但 P2-4 只动了一半

- **不会造出比 `nominalEnd` 更晚到期的假长尾**：`env/TailLedger.java:112`
  是 `Math.min(nominalEnd, Math.max(em[1] + 1L, start + 1L))`——外层 `min` 恒钳住名义到期，
  下限只把窗口往**短**方向抬。这点我按 `tailAlive`（`env/TelegraphBudget.java:140-157`）的求交
  复算过：`end` 变大只会让 `[start,end)` 与 `[now-life,now)` 的交集更长，而 `end <= nominalEnd`
  是恒等式 ⇒ 提问里那个"虚假长尾"不成立。✓
- **P3-5 真关掉**：`book` 现在返回 `boolean`（`:140-158`），`retire` 原样交出（`:113`），
  且 `:157` 那一句 `return entries.containsKey(mirrorKey)` 放在溢出逐出**之后**——
  "入账即被逐出"这一支现在会说 false。两条语义（`:141` 拒入账 / `:157` 被逐出）在实现上都不撒谎了。✓

### 2-A（P2）`start+1` 的下限保住了"记上不记上"，但**记上的长度**在时钟落后时塌成 1 tick ⇒ 仍然低报，最多低报 `particleLife` 倍

**【已核到 path:line】** `env/TailLedger.java:112` 与 `:140-141`；时基来源
`client/TelegraphClient.java:209`（`done.startGameTime`/`done.endGameTime` 是**服务端时基**）
vs `client/TelegraphClient.java:380 + :404`（`noteEmission` 的 `tick` 是 `mc.level.getGameTime()`，**客户端本地时基**）。
被指控的那句判据在 `env/TelegraphBudget.java:101-103`——`clockTooFarBehind` 只挡
`now < start - span`，**明确放行 `now < start`**（落后但不超过一整个发射窗口照样画）。

设服务端登记 `start = S`、名义 `end = E`（`E - S = span`），客户端钟落后 `L >= 1`，
即这条圈最后一次真发射记在 `em[1] = C <= S - 1`。则

```
end = min(E, max(C + 1, S + 1)) = min(E, S + 1) = S + 1     （E > S+1 时）
```

尾段窗口于是是 `[S, S+1)`——**长度 1 tick**，而这条圈实际发射过的是
`[C_first, C_last]` 一大段客户端 tick。后果按 `tailAlive`（`env/TelegraphBudget.java:156`）
`rate × min(span, life)` 算：账面最多 `rate × 1`，真实场上还站着 `rate × min(life, 已发射 tick 数)`
≈ `rate × life`（dust 48 / END_ROD 71）⇒ **低报一个数量级到几十倍**，正好是全局闸
（`env/TelegraphBudget.java:53` 的 `MAX_LIVE_GLOBAL = 2000`）唯一在防的那个方向。
而 `now <= start` 那一支的兜底（`:152-154`）在这里也救不了：它交出的"一生峰值"是
`rate × min(life, emissionSpan(S, S+1)) = rate × min(life, 1) = rate`——同一个 1 tick。

为什么这一条不算重复开轮 22 P2-4：那一条的症状是"整条拒记（账面 0）"，修法（钉下限）
**把症状改成了"账面非 0 但仍然错"**，且改完之后**再没有一条判据能看出它错**——
`retire` 返回 true，测试全绿。本仓对"低报＝危险方向"的定级一直是 P2。

建议（择一，都比现在便宜）：
1. `emissions` 里除了 `[0]=峰值率`、`[1]=最后发射 tick` 再存一个 `[2]=首次发射 tick`，
   `retire` 用**发射过的 tick 数**（`C_last - C_first + 1`，与两个时刻同基，差值免除了时基偏移）
   直接决定尾段窗口长度：`end = start + max(1, min(nominalEnd - start, count))`。
2. 或者把"这条圈记不记尾段"彻底改成不依赖时间量：`em[2]` 存累计发射 tick 数，
   账本条目带一个 `emittedTicks` 字段，`tailAlive` 的 `span` 用它而不是 `end - start`。
   这样时基只在一个地方出现。

### 2-B（P3）`retire` 的两条 false 语义在两个调用点都被**丢弃**，"低报"至今不可观测

### 2-C（P3）`-1L` 哨兵与 `key()` 的键空间重叠（同族：哨兵值撞真实数据）

**【已核到 path:line】** `env/TailLedger.java:72`（`long oldestKey = -1L;`）与 `:80`

### 3-A（P2）搬过去的是一个"真值表"，判据与记账点的**联结**仍然只靠代码位置——轮 22 P2-7 换了名字没关掉

**【已核到 path:line】** 断言侧 `test/StateSelfTest.java:888-892`（`gateTable` 五条：三假、三门各自为真、全真），
被测侧 `env/TelegraphBudget.java:119-121`（`return !culledByDistance && !outOfBudget && !clockBehind;`），
唯一调用点 `client/TelegraphClient.java:398`。
`gateTable` 逐字就是 `!a && !b && !c` 的真值表——**它复述实现**，正是本仓定义的那一类废断言
（引被测类的式子再算一遍）。后果可验证：

- 变异 A：把 `:404` 的 `noteEmission` 挪到 `:398` 的 `return` 之前（＝轮 22 点名的"幽灵账"方向）
  ⇒ `gateTable` 全绿、150 条全绿。
- 变异 B：把 `if (!emitsThisTick(...)) return;` 整条删掉（无条件撒粒子＋无条件记账）
  ⇒ 同样全绿。
- 只有当有人改**判据本身**（比如把 `&&` 改成 `||`）才会红，而那正是最不容易写错的一部分。

`env/TelegraphBudget.java:109-113` 的 javadoc 与 `test/StateSelfTest.java:885-887` 的注释都写着
"第一次能在最快的门上跑红 / 缺门方向＝低报＝危险方向"——这句话现在**不成立**，被红到的只有真值表。
提交信息里"把'哪一 tick 算真发射'从 client/* 的三个 early-return 相对位置搬进自检看得见的纯函数"
同样是搬了一半：**判据可见了，判据与事实的绑定关系仍然不可见**。

建议（比 `OutlineFrame` 便宜、且真正做到"位置改不动"）：让纯函数**交出要记的那个值**，
而不是交出一个布尔再让调用方自己去读 `plan.ratePerTick()`：

```java
// env/TelegraphBudget
public static Outline emissionOrZero(boolean culledByDistance, Outline plan, boolean clockBehind) {
    return (culledByDistance || plan.empty() || clockBehind) ? Outline.NONE : plan;
}
```
调用点变成 `Outline emit = emissionOrZero(culledByDistance, plan, clockBehind); if (emit.empty()) return;
TAILS.noteEmission(z.mirrorKey, emit.ratePerTick(), now); ... for (int k = 0; k < emit.ratePerTick(); k++)`
——这样"记的率"与"撒的个数"是**同一个对象的同一个字段**（顺带把轮 22 P2-7 后半句
"率 == `addAlwaysVisibleParticle` 调用次数"也变成构造性成立），而自检断言
"任一条件成立 ⇒ 交回的 `Outline` 是 NONE、`ratePerTick()==0`"判的是一个**有内容的返回值**，
上面两个变异都能红。

### 3-B（P3）纯类 javadoc 说"三道门"，客户端实际至少五道：`hasStyle` 与到期 `continue` 都在函数之外

**【已核到 path:line】** `client/TelegraphClient.java:230`（`if (!hasStyle(z.visual)) spawnOutlineParticles(...)`）
与 `:226`（`if (z.endGameTime <= now) continue;`）。两处都让一条在途圈这一 tick **既不撒粒子也不记发射事实**，
但 `env/TelegraphBudget.java:106-118` 的措辞是"这一 tick 这条圈会不会真的往世界里撒粒子——**三道门**任一成立就不撒"，
参数表也只列了三个。几何档（`hasStyle` 为真）不记账是**对的**（线框不是粒子，尾段无物可记），
但函数名与 javadoc 读起来像"这三条就是全部"，下一个人会拿 `emitsThisTick` 当
"这条圈这一 tick 有没有被玩家看见"的判据——那个语义里几何档是在看的。
另一半风险更实际：`hasStyle` 依赖 `STYLES`（`:100`），而 `registerStyle`（`:114`）是 public 且随时可被调，
所以第四道门是**运行期可变**的，纯类里没有任何一处登记它。
建议二选一：给 `emitsThisTick` 加第四个参数（`handledByGeometryRenderer`），或者把 javadoc 第一句
改成"本函数只覆盖粒子档；几何档另由 `TelegraphClient.hasStyle` 分流，它不记发射事实是因为它不撒粒子"。
